# Mixed Scheduling 实测报告

对照：上一版 CUDA 融合（Fusion）vs CUDA 融合 + Decode-priority Mixed Scheduling（Mixed）。

## 环境与方法

GPU：NVIDIA GeForce RTX 5080；PyTorch：2.11.0+cu128；dtype：torch.bfloat16。
模型为本机 Qwen3-0.6B；单 GPU、WSL Ubuntu 24.04，CUDA Toolkit 12.8。两版启用相同两项 CUDA 融合、相同 CUDA Graph 设置和采样参数。
每个场景/预算/实现共 6 次：A/B、B/A 两种独立进程顺序，各重复 3 次。以下主值为每次统计的中位数；不是大规模线上负载或置信区间。
先通过 correctness 再运行 benchmark。计时排除模型加载、编译、Graph capture 和预热；包含输入准备、模型、采样与调度的实际运行开销。
详细负载、时间戳含义、复现命令见 [实现说明](MIXED_SCHEDULING.md)。原始 JSON 和日志在 `results_mixed/`。

## 正确性与保护检查

22 项 unittest 全部通过：7 项已有融合测试、13 项 scheduler 测试、2 项 Engine/GPU metadata 测试。另有独立审查的 100 轮紧张容量/共享 prefix CPU 随机验证。
完整模型：budget 128/512/1024 + Graph ON，以及 budget512 + Graph OFF，均通过；4 组单请求原采样 token_ids 完全一致。
64 个有效 request/position logits 行：最大 relative L2=0.025394，最小 cosine=0.999707，最大绝对差=0.187500；top1 一致 64/64。
预设阈值 relative L2<0.03、cosine>0.999。两版 teacher-forced token 历史一致；以上证明限定于已测样本与容差，不声称混合随机采样整段输出 bitwise 相同。
原仓库 26 个跟踪文件、上一版融合副本 39 个文件哈希均保持不变。
新副本中，旧生产文件仅 scheduler.py、llm_engine.py 改动；另新增 schedule_output.py。原 CUDA kernel 与模型执行代码未改。

## 结果解读与边界

以 budget512、单条 3000-token 长 prompt 加 4 条 decode 为例：step 边界最大停顿 94.47 → 20.78 ms；新请求 step TTFT 90.05 → 107.54 ms；输出吞吐 710.03 → 708.86 tok/s。
调度改变了 decode 的执行机会，没有加速单个 prefill kernel。Mixed 的两条 GPU 路径顺序执行，长 prompt 的每个 chunk 仍会影响下一轮 decode；更小预算缩短单次 chunk，但可能增加调用次数和开销。
连续 prefill 导致的最大停顿与常态 TPOT 是不同指标：baseline 的首个超长等待可能被平均 TPOT（从首 token 起算）排除，也容易被 p95 掩盖，因此必须同时报告最大 gap。
输出 throughput、TTFT 和 E2E 是否改善取决于预算和负载。纯 decode 没有 mixed 调度机会，小幅差异需结合测量范围。纯 prefill 的组批也可能变化：原实现只允许首个请求切块，新实现允许尾部请求填满剩余预算；例如 budget512 的四轮 token 数从 300/500/512/488 变成 512/512/512/264。因此纯 prefill 的差异不能全部归因于 decode 优先，也不能直接泛化成稳定加速。
本次性能实验 KV 容量充足；紧张容量的抢占与 prefix 正确性主要由状态测试验证，没有测量内存压力下的线上尾延迟。持续高负载下的公平性、多 GPU、网络 streaming、GPU utilization 和 Nsight timeline 未测。
